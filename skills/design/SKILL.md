# Design a change

For consequential TypeScript data shapes or boundary choices, read [TypeScript guidance](references/typescript.md).

Read [core values](../pancake/references/values.md) and applicable repository instructions. Establish the requested outcome, constraints, and what is outside scope from the user's request and available context. Ask only when a missing product decision materially changes the design.

Inspect the relevant implementation, callers, tests, and documented contracts. Identify who owns the data and behavior, and which boundaries the change crosses. Cite inspected locations that constrain the proposal. For greenfield work, state assumptions rather than inventing an existing architecture. Distinguish documented rationale from inferred intent.

Start with an example of how a caller or user would use the proposed change. Derive the necessary data shapes, interfaces, and ownership from that example. Name the meaningful variants and invariants in the data shape. Prefer a structure that expresses valid states over combinations of flags or optional fields that callers must keep synchronized. Use existing types and conventions when they already fit. Describe state transitions, failure handling, or persistence only when relevant. Keep sketches in the response unless the user requests a written artifact. Do not add stub files or change code merely to present a design.

For shared or stateful behavior, name the owner of each mutable value and domain rule. Identify who creates, updates, persists, and releases it, and which callers can observe it. Keep validation at relevant external boundaries and avoid duplicating internal rules across callers. If concurrent actors share state, consider separating ownership before adding coordination.

At a trust boundary, identify the raw input, authoritative contract, parsing or validation owner, and resulting domain value or error. Static annotations do not validate JSON, configuration, network payloads, or persisted records at runtime. Reuse established parsers and schema-derived types when available rather than maintaining competing definitions. Keep transport and framework conversion at the boundary unless exposing those representations is an intentional contract.

Use domain types to prevent demonstrated mistakes, such as interchangeable identifiers or contradictory state variants, with the target language's established idioms. Make relevant variant handling explicit and exhaustive where supported. Do not use casts or assertions as evidence that external data is valid. After validation, avoid repeating the same guard throughout internal calls; retain checks required by mutable state, trust changes, or actual runtime constraints. Separate domain decisions from I/O and framework wiring when it materially improves clarity or verification, without forcing wrappers or a language migration.

Check the usage sketch for abstraction leaks. Callers should not need hidden sequencing rules, internal representations, or repeated conversions to use the interface correctly. Prefer a boundary that owns coherent domain knowledge and hides useful complexity. Avoid pass-through layers that only rename calls or modules organized solely around execution phases. Keep a direct local function when a new abstraction would add more burden than it removes.

Compare alternatives when the choice has meaningful consequences. Include extending the existing design when viable. Explain the concrete tradeoff that decides the recommendation, such as compatibility, maintenance, performance, or operational cost. A small local change may need only a short recommendation. A consequential architectural choice benefits from structurally different alternatives. Do not require a fixed number of designs, agents, or providers.

For an unfamiliar interaction or an unresolved architectural choice, compare concrete sketches that differ in ownership, interaction, or data flow rather than cosmetic variations of one idea. Use the same representative user or caller scenario and constraints for each. Explain the difference that decides the recommendation. Skip additional exploration when an established pattern or a hard constraint already settles the shape.

Judge alternatives from the consumer's perspective as well as the maintainer's. Consider the central task, discoverability, useful feedback, failure recovery, and the burden of calling or changing the interface where relevant. Do not choose a confusing workflow solely because it is easier to implement, or add controls and options without a demonstrated need. Make feasibility, compatibility, accessibility, and operating cost part of the tradeoff instead of assuming experience overrides every constraint. Prefer a focused, complete core flow over speculative breadth. Label subjective preferences separately from observed results; use authorized experiments only when they can settle the remaining uncertainty.

If an uncertain behavior decides the design, seek narrow evidence from existing checks or inspection. Label estimates and untested assumptions. For an authorized experiment, use [measured experiments](../pancake/references/experiments.md). A prototype that writes files, starts services, or changes configuration requires authorization appropriate to those actions; a design request alone remains read-only.

When a new requirement challenges the existing architecture, distinguish necessary contracts from incidental structure. Sketch how the relevant behavior would be organized if the new constraint had been known from the start. Compare that shape with a focused extension of the current design. Preserve compatibility and useful work where required; first-principles reasoning is not permission for a broad rewrite.

For substantial implementation, identify the types, boundaries, or verification support that genuinely unblock dependent units. Sequence those foundations before their consumers. Prefer existing infrastructure when sufficient and avoid scaffolding for speculative phases. Trace the dominant reads, writes, and transitions to check that the chosen structure serves real usage.

For a migration, describe the target state, affected callers and data, observable completion criteria, and how the old path will be retired. Name any necessary compatibility period and its removal condition. Avoid temporary adapters that solve no actual transition requirement. If intermediate breakage is proposed, make its scope, recovery, and verification boundary explicit; do not assume it is acceptable in shared branches or deployed systems. Keep implementation and delivery authorization separate from the proposal.

For commands or lifecycle operations that may repeat, describe the result of a second invocation and recovery after partial completion. Inspect existing state before repeating a side effect. Use stable operation identities, atomic transitions, or reconciliation where the actual contract warrants them. Do not claim exactly-once behavior from a local flag or retry alone. For non-idempotent external effects, identify duplicate-prevention and ambiguous-outcome handling explicitly. Include relevant repeat, interruption, and recovery scenarios in the verification plan rather than adding a universal retry layer.

For internal API replacement, inventory relevant callers and migrate them before removing the old path. Prefer one coordinated change when scope and compatibility permit it. Check external, persisted, or independently deployed consumers before assuming every caller can move together. A necessary compatibility path needs an owner, retirement condition, and verification; preserving it temporarily is justified by a real consumer requirement, not by avoiding caller migration.

When mutable state must be shared, identify the actual invariant requiring it and the operation that must be atomic. Prefer separate owned state when actors produce independent results. For genuinely shared state, use structural coordination appropriate to the system, such as a single writer, transaction, or supported synchronization primitive. A convention in a prompt or a check-then-write sequence does not prevent concurrent updates. Account for failure and release of ownership without assuming a process identifier alone proves a lock is stale.

Recommend the simplest sufficient approach. Identify affected contracts, migration needs, and material risks. Describe a focused verification plan tied to the intended outcome, distinguishing proposed checks from checks already performed. For larger work, outline an implementation sequence that can be verified incrementally.

Lead with the recommendation. Include the usage sketch, decisive tradeoffs, and verification plan only to the depth the task needs. Leave unresolved decisions explicit. Stop at the proposal unless implementation was also requested. If authorized implementation repeatedly needs similar workarounds, inspect the shared premise before adding another exception. Repeated casts, synchronized flags, unexpected shared-state coordination, or callers depending on internals can indicate a faulty shape. Distinguish a recurring design problem from legitimate isolated complexity. Trace the affected behavior, revise the proposal to account for the new constraint, and identify caller migration and verification needs. Preserve correct work; revising a design does not authorize deleting artifacts or widening implementation scope.
