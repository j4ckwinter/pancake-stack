# Design state ownership and recovery

For shared or stateful behavior, name the owner of each mutable value and domain rule. Identify who creates, updates, persists, and releases it, and which callers can observe it. Keep validation at relevant external boundaries and avoid duplicating internal rules across callers. If concurrent actors share state, consider separating ownership before adding coordination.

For commands or lifecycle operations that may repeat, describe the result of a second invocation and recovery after partial completion. Inspect existing state before repeating a side effect. Use stable operation identities, atomic transitions, or reconciliation where the actual contract warrants them. Do not claim exactly-once behavior from a local flag or retry alone. For non-idempotent external effects, identify duplicate-prevention and ambiguous-outcome handling explicitly. Include relevant repeat, interruption, and recovery scenarios in the verification plan rather than adding a universal retry layer.

When mutable state must be shared, identify the actual invariant requiring it and the operation that must be atomic. Prefer separate owned state when actors produce independent results. For genuinely shared state, use structural coordination appropriate to the system, such as a single writer, transaction, or supported synchronization primitive. A convention in a prompt or a check-then-write sequence does not prevent concurrent updates. Account for failure and release of ownership without assuming a process identifier alone proves a lock is stale.
